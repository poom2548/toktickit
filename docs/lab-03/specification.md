# เอกสารข้อกำหนดระบบ (System Specification) - Lab 3

> [!CAUTION]
> **การบังคับใช้เกตเวย์ (Gateway Enforcement):** ห้ามเปิดสาขา (Branch) สำหรับการเขียนโค้ด (Implementation) ใด ๆ จนกว่าเอกสารทั้งสี่ฉบับนี้ (`specification.md`, `ui-spec.md`, `api-spec.md`, และ `tests.md`) จะถูกคอมมิตและพร้อมใช้งานใน `docs/lab-03/` อย่างสมบูรณ์

## 1. เป้าหมายของสปรินต์ (Sprint Goal)
เป้าหมายของสปรินต์นี้คือการพัฒนาระบบ TokTickIT ให้มีความสมบูรณ์ด้วยการนำระบบการยืนยันตัวตน (Authentication) และการกำหนดสิทธิ์ตามบทบาท (Role-based Authorization) มาใช้จริงแทนที่ตัวเลือกแบบชั่วคราว พร้อมทั้งเปิดใช้เวิร์กโฟลว์สำหรับผู้ใช้งานกลุ่ม `IT_STAFF` ในการจัดการคิวตั๋ว และระบบการจัดการผู้ใช้งานสำหรับกลุ่ม `ADMINISTRATOR`

## 2. สรุปความต้องการของผู้มีส่วนได้ส่วนเสีย (Stakeholder Request Summary)
ผู้มีส่วนได้ส่วนเสียต้องการให้ระบบปรับเปลี่ยนจากการเลือกผู้ใช้งานชั่วคราว (Dev Requester selector) ไปสู่การใช้ระบบล็อกอินด้วยบัญชีจริง โดยมีข้อกำหนดให้ผู้ใช้งานต้องเปลี่ยนรหัสผ่านเมื่อเข้าสู่ระบบครั้งแรกเสมอ ระบบจะต้องมีการนำทาง (Navigation) ที่แสดงผลแตกต่างกันตามบทบาทของผู้ใช้ ในส่วนของผู้ใช้กลุ่ม `REQUESTER` จะต้องยังคงสามารถทำเวิร์กโฟลว์เดิมจาก Lab 2 ได้ครบถ้วนภายใต้บัญชีจริง และเพิ่มความสามารถในการแสดงความคิดเห็นแบบสาธารณะและทำเครื่องหมายเมื่อปัญหาได้รับการแก้ไขแล้ว สำหรับผู้ใช้งานกลุ่ม `IT_STAFF` จะต้องมีระบบคิวตั๋วและหน้ารายละเอียดตั๋วเพื่อใช้ในการทำงาน และสำหรับกลุ่ม `ADMINISTRATOR` จะต้องสามารถจัดการผู้ใช้งานในระบบได้ ทั้งนี้ ทุกการกระทำจะต้องถูกควบคุมความปลอดภัยด้วยการตรวจสอบสิทธิ์ฝั่งเซิร์ฟเวอร์ในระดับ API อย่างเข้มงวด

## 3. ขอบเขตของระบบ (Scope)

**ส่วนที่อยู่ในขอบเขต (In Scope):**
- การยืนยันตัวตน (การล็อกอิน, การล็อกเอาต์, การดึงข้อมูลผู้ใช้ปัจจุบัน, การบังคับเปลี่ยนรหัสผ่านเมื่อใช้งานครั้งแรก)
- การนำทางในแอปพลิเคชันแบบแบ่งตามบทบาท และการป้องกันสิทธิ์ในฝั่งเซิร์ฟเวอร์
- การย้ายข้อมูลจาก Dev Requester ไปเป็นโมเดล User สำหรับผู้ใช้ที่ผ่านการยืนยันตัวตน
- การทดสอบการถดถอยสำหรับ `REQUESTER` (เวิร์กโฟลว์ของ Lab 2 ทั้งหมดต้องทำงานได้ด้วยตัวตนจริง)
- `REQUESTER`: การแสดงความคิดเห็นแบบสาธารณะในตั๋วของตนเอง
- `REQUESTER`: การทำเครื่องหมาย "ปัญหาดูเหมือนจะได้รับการแก้ไขแล้ว" (Problem Appears Resolved flag)
- คิวตั๋วสำหรับ `IT_STAFF` พร้อมระบบค้นหา ตัวกรอง การเรียงลำดับ และการแบ่งหน้า (Pagination)
- หน้ารายละเอียดตั๋วสำหรับ `IT_STAFF`: การอ้างสิทธิ์/เปลี่ยนเจ้าของตั๋ว, การตั้งค่าความสำคัญทางไอที (IT Priority), การเปลี่ยนสถานะ, การแสดงความคิดเห็นแบบสาธารณะ และบันทึกข้อความภายใน (Internal Notes)
- การจัดการผู้ใช้งานสำหรับ `ADMINISTRATOR`: แสดงรายการ, สร้าง, แก้ไข (ชื่อ, อีเมล, บทบาท, สถานะใช้งาน), ตั้งค่ารหัสผ่านเริ่มต้น
- ความต่อเนื่องของการออกแบบในระบบ Zen Green
- ขั้นตอนการทำงานผ่าน GitHub Branching และการตรวจทานโค้ด (Peer Review)

**ส่วนที่อยู่นอกขอบเขต (Out of Scope):**
- การส่งอีเมลคำเชิญ, อีเมลรีเซ็ตรหัสผ่าน, การยืนยันตัวตนแบบหลายปัจจัย (MFA), การล็อกอินผ่านโซเชียล, การใช้งาน SSO
- การสมัครสมาชิกด้วยตนเองโดยกลุ่ม `REQUESTER`
- การบันทึกการดำเนินการของ `IT_STAFF` (Actions Taken) (ถูกเลื่อนไปอยู่ใน Lab 4)
- การคำนวณระยะเวลาตามข้อตกลงระดับบริการ (SLA), กฎการส่งต่อปัญหา (Escalation Rules), บริการการแจ้งเตือน
- แดชบอร์ดหรือการวิเคราะห์ข้อมูล KPI
- ระบบหลายองค์กร / หลายแผนก (Multi-tenant)
- การลบผู้ใช้งาน, การดำเนินการเป็นชุด (Bulk Operations), การนำเข้า/ส่งออก, ประวัติบัญชี
- การกำหนดบทบาทมากกว่าหนึ่งบทบาทต่อผู้ใช้หนึ่งคน
- แผนก/องค์กร, รูปโปรไฟล์, การจัดการโปรไฟล์แบบขยาย
- การปลดล็อกบัญชี, ขั้นตอนการอนุมัติแอดมิน
- การแบ่งหน้าสำหรับรายการผู้ใช้งาน, การเรียงลำดับหลายคอลัมน์พร้อมกัน, การกรองหลายฟิลเตอร์พร้อมกัน
- การปรับใช้ขึ้นระบบจริง (Production Deployment) หรือโครงสร้างคลาวด์
- การแก้ไขหรือลบความคิดเห็นแบบสาธารณะหรือบันทึกข้อความภายใน (เป็นแบบเพิ่มได้อย่างเดียว)

## 4. ข้อกำหนดการทำงาน (Functional Requirements - FR)
- **FR-01 (Authentication):** ระบบต้องรองรับการล็อกอินด้วยอีเมลและรหัสผ่าน โดยเก็บเซสชันเป็นแบบ HttpOnly ข้อมูลผู้ใช้งานที่ส่งกลับจาก `GET /auth/me` ต้องไม่มี `passwordHash` เมื่อล็อกเอาต์ ระบบต้องยกเลิกเซสชัน และหากบัญชีมีสถานะบังคับเปลี่ยนรหัสผ่าน จะต้องปิดกั้นทุกเส้นทาง (Routes) จนกว่าจะเปลี่ยนรหัสผ่านสำเร็จ
- **FR-02 (Password Rules):** รหัสผ่านต้องมีความยาวขั้นต่ำ 8 ตัวอักษร ต้องถูกแฮชด้วย `bcrypt` หรือ `argon2` ห้ามเก็บเป็นข้อความปกติเด็ดขาด และในกรณีล็อกอินล้มเหลว ระบบจะต้องไม่เปิดเผยว่าบัญชีไม่มีอยู่จริงหรือรหัสผ่านผิด
- **FR-03 (Role-Based Navigation):** โครงสร้างแอปพลิเคชัน (App Shell) ต้องแสดงชื่อผู้ใช้และบทบาท เมนูการนำทางต้องแสดงเฉพาะตามบทบาทที่มีสิทธิ์ และการเข้าถึงหน้าที่ไม่มีสิทธิ์จะต้องแสดงหน้าจอที่ถูกปฏิเสธ (Forbidden)
- **FR-04 (Requester Regression):** การดำเนินการทุกอย่างเกี่ยวกับ Ticket และ Attachment ของ `REQUESTER` ต้องใช้ `req.user.id` โดยระบบจะเพิกเฉยต่อ `requesterId` ที่ส่งมาใน Request Body และหาก `REQUESTER` พยายามเข้าถึงตั๋วของผู้อื่น ระบบจะต้องตอบกลับด้วยรหัส 403 โดยไม่เปิดเผยข้อมูลใดๆ
- **FR-05 (Requester Public Comments):** ผู้ใช้สามารถใช้ `POST` และ `GET` บนตั๋วของตนเองได้ ข้อความต้องไม่ว่างเปล่าและไม่เกินขีดจำกัดที่กำหนด และต้องจัดเก็บพร้อม `authorId` และ `createdAt`
- **FR-06 (Requester Resolved Flag):** ต้องสามารถตั้งค่าสถานะค่าความจริง (Boolean) เพื่อระบุว่าปัญหาได้รับการแก้ไขแล้ว (Problem Appears Resolved) ซึ่งการกระทำนี้ต้องไม่เปลี่ยนสถานะของตั๋วเป็น `RESOLVED` อัตโนมัติ แต่จะแจ้งเตือนให้ `IT_STAFF` ทราบ
- **FR-07 (IT Staff Queue):** ระบบ `GET /staff/tickets` ต้องรองรับการค้นหา (สรุป และหมายเลขตั๋ว), ตัวกรองสถานะ, ตัวกรองความสำคัญ, ตัวกรองเจ้าของตั๋ว, การเรียงลำดับ (ฟิลด์และทิศทาง), การแบ่งหน้า (หน้าและขนาดหน้า) พร้อมคืนค่ารายละเอียดการแบ่งหน้า (Pagination Metadata)
- **FR-08 (IT Staff Queue UI):** ระบบแสดงผลคิวตั๋วต้องเป็นรูปแบบตาราง (สำหรับเดสก์ท็อป) หรือรูปแบบการ์ด (สำหรับมือถือ) โดยมีคอลัมน์/ข้อมูลครบถ้วน เช่น หมายเลขตั๋ว, วันที่สร้าง, สรุป, หมวดหมู่, ความสำคัญที่ร้องขอ, ความสำคัญทางไอที, สถานะ, เจ้าของตั๋ว, และอัปเดตล่าสุด
- **FR-09 (IT Staff Detail):** ระบบ `GET /staff/tickets/:id` ต้องแสดงรายละเอียดทั้งหมด (ตั๋ว, ข้อมูลผู้ร้องขอ, เจ้าของตั๋ว, ความคิดเห็น, บันทึกภายใน, ไฟล์แนบ) รองรับ `PATCH` สำหรับเจ้าของ, ความสำคัญ และสถานะ โดยกฎการเปลี่ยนสถานะต้องถูกตรวจสอบฝั่งเซิร์ฟเวอร์
- **FR-10 (Internal Notes):** รองรับ `POST`/`GET` เฉพาะผู้มีบทบาท `IT_STAFF` และ `ADMINISTRATOR` เท่านั้น หากเป็น `REQUESTER` ต้องส่งรหัส 403 และไม่มีข้อมูลรั่วไหล
- **FR-11 (Admin User Management):** ระบบ `GET /admin/users` รองรับการค้นหาและกรองบทบาท, `POST /admin/users` สร้างผู้ใช้ใหม่พร้อมสถานะ `requiresPasswordChange=true`, `PATCH /admin/users/:id` รองรับการแก้ไขข้อมูล, และ `PATCH /admin/users/:id/password` เพื่อตั้งค่ารหัสผ่านใหม่
- **FR-12 (Admin Safety Rules):** ป้องกันไม่ให้แอดมินปิดการใช้งานตนเอง ป้องกันการปิดการใช้งานแอดมินคนสุดท้ายที่ยังทำงานอยู่ ป้องกันอีเมลซ้ำ และตรวจสอบรับเฉพาะบทบาทที่ถูกต้อง
- **FR-13 (Secrets):** ห้ามนำข้อมูลลับใดๆ คอมมิตลง Repository โดยให้ใช้ไฟล์ `.env.example` เป็นโครงร่างพร้อมค่าทดแทนเท่านั้น

## 5. กฎทางธุรกิจ (Business Rules - BR)
- **BR-01:** ห้ามจัดเก็บรหัสผ่านในรูปแบบข้อความปกติ ต้องใช้การแฮชด้วย `bcrypt` หรือ `argon2` เสมอ
- **BR-02:** ผู้ใช้ที่มีสถานะ `requiresPasswordChange = true` จะต้องทำขั้นตอนการเปลี่ยนรหัสผ่านให้เสร็จสิ้นก่อนเข้าถึงหน้าจออื่น
- **BR-03:** ค่า `requesterId` ในการดำเนินการกับตั๋วต้องมาจาก `req.user` เสมอ ค่า `requesterId` ที่ลูกค้าส่งมาจะถูกเพิกเฉย
- **BR-04:** ข้อความบันทึกภายใน (Internal Notes) สงวนไว้สำหรับ `IT_STAFF` และ `ADMINISTRATOR` เท่านั้น การร้องขอจาก `REQUESTER` จะได้รับ `403`
- **BR-05:** มีเพียง `IT_STAFF` และ `ADMINISTRATOR` ที่สามารถตั้งสถานะตั๋วเป็น `RESOLVED` หรือ `CLOSED` ได้ ธงบอกสถานะจาก `REQUESTER` จะไม่เปลี่ยนสถานะโดยตรง
- **BR-06:** เจ้าของตั๋วต้องเป็นผู้ที่มีบทบาท `IT_STAFF` หรือ `ADMINISTRATOR` เท่านั้น หากตั้งค่าผู้ใช้ที่ไม่เหมาะสมจะได้รับข้อผิดพลาดรหัส `422`
- **BR-07:** `ADMINISTRATOR` ไม่สามารถปิดการใช้งานบัญชีของตนเองได้
- **BR-08:** ระบบจะต้องมี `ADMINISTRATOR` ที่กำลังใช้งานอยู่อย่างน้อย 1 คนเสมอ หากทำผิดเงื่อนไขจะถูกปฏิเสธ
- **BR-09:** อีเมลจะต้องไม่ซ้ำกันในระบบผู้ใช้ทั้งหมด การซ้ำจะส่งรหัสผิดพลาด `409`
- **BR-10:** บทบาทที่อนุญาตมีเพียง `REQUESTER`, `IT_STAFF`, `ADMINISTRATOR` เท่านั้น ค่าอื่นจะถูกปฏิเสธรหัส `422`
- **BR-11:** ห้ามนำความลับในการยืนยันตัวตน (เช่น JWT secret, Session secret) เข้าสู่ Source Control
- **BR-12:** การตอบสนองข้อผิดพลาดจากการล็อกอินต้องไม่แยกความแตกต่างระหว่าง "รหัสผ่านผิด" และ "บัญชีไม่ทำงาน" (ป้องกันการระบุบัญชีผู้ใช้)

- คำขอที่ไม่ผ่านการยืนยันตัวตนไปยัง Endpoint ที่ถูกป้องกันจะได้รับรหัส `401`
- คำขอที่ผ่านการยืนยันตัวตนแต่พยายามเข้าถึง Endpoint ที่ไม่ได้รับอนุญาตจะได้รับรหัส `403`
- หาก `REQUESTER` พยายามเข้าถึงตั๋วของผู้อื่น จะได้รับรหัส `403` โดยไม่ระบุความมีอยู่ของตั๋วนั้น

## 7. เมทริกซ์การเปลี่ยนสถานะตั๋ว (Ticket Status Transition Matrix)

## 8. เกณฑ์การยอมรับ (Acceptance Criteria - AC)

*(เกณฑ์การยอมรับที่กำหนดในรูปแบบ Given/When/Then จำแนกตาม Issue)*

**Issue #1 — Engineering Contract**
- **AC-SPEC-01:** **Given** สถานะก่อนการพัฒนา **When** ตรวจสอบไฟล์ `specification.md` **Then** จะต้องมีเนื้อหาส่วนต่างๆ อย่างครบถ้วนรวมถึงเป้าหมาย, ขอบเขต, และข้อกำหนด FR, BR
- **AC-SPEC-02:** **Given** สถานะก่อนการพัฒนา **When** ตรวจสอบไฟล์ `api-spec.md` **Then** จะต้องมีการกำหนดรายละเอียดของทุก endpoint
- **AC-SPEC-03:** **Given** สถานะก่อนการพัฒนา **When** ตรวจสอบไฟล์ `ui-spec.md` **Then** จะต้องมีหน้าจอ กฎเกณฑ์ดีไซน์ และรายการตรวจสอบครบถ้วน
- **AC-SPEC-04:** **Given** สถานะก่อนการพัฒนา **When** ตรวจสอบไฟล์ `tests.md` **Then** จะต้องมีแผนการทดสอบแบบก่อนการพัฒนา (Pre-implementation) ที่ครอบคลุมทุกจุด
- **AC-SPEC-05:** **Given** เอกสารทั้งหมดถูกสร้าง **When** ทำการตรวจสอบความสอดคล้อง **Then** AC ทุกข้อในสเปคต้องถูกกำหนดการทดสอบ และทุก API ต้องสอดคล้อง

## 9. การตัดสินใจเรื่องการย้ายข้อมูล (Migration Decisions)
- ข้อมูลตั๋ว, ไฟล์แนบ, หมวดหมู่ และระบบที่เกี่ยวข้องที่ตั้งอยู่เดิม จะต้องคงอยู่ในกระบวนการย้ายข้อมูล (Migration) โดยไม่เกิดความสูญเสียทางข้อมูล (Zero Data Loss)
- ข้อมูลชั่วคราว Dev Requester จะถูกโอนย้ายไปยังแถว User จริงโดยมีสถานะ `role=REQUESTER` ตั้งค่ารหัสผ่านเริ่มต้น และ `requiresPasswordChange=true`
- ความสัมพันธ์คีย์นอก (Foreign Key) `requesterId` ในแต่ละตั๋วจะอ้างอิงไปยังแถว User ที่ถูกย้ายไปอย่างถูกต้อง
- ส่วนต่อประสาน (UI) การเลือก Dev Requester ถูกนำออกทั้งหมดจากฝั่งไคลเอนต์
